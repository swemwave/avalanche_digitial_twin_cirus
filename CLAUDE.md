# CLAUDE.md — Orientation for AI Agents

**Read this first. It tells you what this repository is, where to work, and which rules you must not break.**

> **Stage 3 ("Ultra").** This project was radically simplified. It is now a single-screen
> avalanche digital twin with four features and a runtime that reads **no source data at all**.
> If a doc, comment, or memory describes weather ingestion, a job queue, a SQLite database, five
> research tabs, `/api/v1`, susceptibility scoring, or ~35 endpoints, it describes the **superseded**
> pre-Stage-3 build. Trust this file and the code.

---

## 1. What this project is

A **Mount Hosmer avalanche digital twin**: a local, offline research prototype for one mountain near
Fernie, BC. The fixed area of interest (AOI) is a single ~12×12 km mountain — this is a single-mountain
study, not a general-purpose GIS platform.

Stage 3 keeps exactly **four things**:

1. **3D terrain mesh** — a real 5 m LiDAR mesh (99.9 % AOI coverage), with hillshade and a baked
   winter Sentinel-2 natural-colour surface.
2. **Runout simulation** — fast (alpha-angle) and advanced (particle-ensemble) engines.
3. **A simplified risk model** — one transparent release estimate driven by UI sliders, not weather feeds.
4. **A local AI assistant** — Ollama (`llama3.1:8b`), fully offline; explains an assessment and runs
   what-if scenarios.

Conditions (new snow, wind speed, wind direction, release size) come from **UI sliders / presets**.
There is no weather, snow, or dynamic satellite ingestion. One fixed Sentinel-2 RGB capture is read at
bake time as visual context only; it never enters the risk model and is never read from `DATA\` at runtime.

> **Safety rule, non-negotiable.** This is **not an operational avalanche forecast**. It must never be
> presented as one, and never described as replacing Avalanche Canada forecasts or field assessment.
> Every user-facing surface that shows a hazard/release number must keep its
> "experimental / non-operational" disclaimer. The disclaimer is **attached in code**
> (`app/core/model_config.py::DISCLAIMER`), never generated by the AI, and never optional. Do not
> remove it, and do not add language implying operational reliability.

## 3. The pipeline: bake → baked → serve

Stage 3 has exactly one, strictly one-directional pipeline:

```
DATA\mount_hosmer_data\        (read-only: terrain sources + one fixed Sentinel-2 RGB capture)
        │   python -m app.bake   (ONCE, offline — the only step that touches DATA\ or rasterio/pyproj)
        ▼
  runtime\baked\               tiles\... + imagery\... + layers\*.npy (7 layers) + meta.json
        │
        ▼
  backend\app\main.py          FastAPI, a handful of routes, localhost:8000
        │                      (loads .npy with plain numpy — NO rasterio, NO DATA\ access)
        ▼
  frontend\src\                Next.js + MapLibre, localhost:3000 (single screen)
```

**After the one-time bake, a running Stage-3 app needs nothing from `DATA\`.** The 7 baked layers are
elevation, slope, aspect, plan_curvature, general_curvature, forest_mask, distance_to_ridge.
`meta.json` carries the grid/AOI plus a 21×21 grid→WGS84 control lattice that replaces pyproj at runtime.

Data details: [`docs/data-footprint.md`](docs/data-footprint.md) is the authoritative bake input contract.

## 4. The invariants

Break these and you break the project.

### I1 — `DATA\` is strictly read-only (and bake-time only)
Source data is never modified, renamed, moved, or overwritten. It is expensive to re-download, and some
of it (the Fernie `2C21P` archive) **cannot** be re-downloaded. Only `bake.py` reads it, and only from the
allow-list in [`docs/data-footprint.md`](docs/data-footprint.md). Every generated artifact goes under
`mount-hosmer-digital-twin\runtime\`.

### I2 — The app folder and `DATA\` must stay siblings
Both `backend/app/core/settings.py` and `launcher/Program.cs` independently resolve the data root as
`<project_root>\..\DATA\mount_hosmer_data`. Moving or renaming either folder breaks the bake in two
languages, silently. If you must relocate them, update *both* files, and remember `Program.cs` requires a
.NET 9 rebuild to take effect. (This only bites at bake time now — the running service never reads `DATA\`.)

### I3 — Missing data is reported as missing, never as zero
This is a **safety property**, not a style preference. Baked `.npy` layers load as **masked arrays**
(`np.ma.masked_invalid`), so a NaN pixel is *masked*, not silently 0. And a below-threshold day is **not**
reported as zero hazard: when no release zone crosses the threshold, `assess.py` falls back to the 95th
percentile of the release estimate on avalanche terrain and labels it as such. Never `fillna(0)` a
measurement, never default a missing value to a safe-looking number, never let a gap lower a hazard score.

### Disclaimer — non-negotiable (see §1)
Every hazard/release number carries the `DISCLAIMER`, attached in code, on every surface.

**Lineage note (bake-time reuse, ex-I5).** `python -m app.bake` reuse is existence-only: it skips the
rebuild if `runtime\baked\meta.json` is already there, with no hash check of sources, config, or
parameters. Changing the DEM/config/params does **not** get auto-detected — always run
`python -m app.bake --force` after changing anything upstream of the bake. (An earlier content-hash
cache, keyed on a SHA-256 of sources/config, existed in `app.services.cache` but was only ever wired
into the removed `process-terrain` CLI path; it was dead code and has been deleted rather than revived.)
The *running service* has no processors and no cache to invalidate — it just serves the baked files.

## 5. Common tasks

**Run everything (easiest):** double-click `mount-hosmer-digital-twin\MountHosmerDigitalTwin.exe`.
It resolves paths, runs the bake if `runtime\baked\` is missing, starts both servers, opens the browser.

**Run the pieces by hand:**
```powershell
cd D:\school\capstone\Avalanche\mount-hosmer-digital-twin
python -m app.bake                                       # ONE-TIME: build runtime\baked\ (add --force to rebuild)
python -m uvicorn app.main:app --reload --port 8000      # backend  (needs runtime\baked\)
cd frontend; npm run dev                                 # frontend (localhost:3000)
```

The bake needs the geospatial stack (`pip install -r backend\requirements-bake.txt`); the running
service needs only `backend\requirements.txt` (fastapi/uvicorn/pydantic/numpy/scipy/shapely/httpx).

**The AI assistant (optional, fully local):** install Ollama, then `ollama serve` and
`ollama pull llama3.1:8b`. Without it, the assistant endpoints return a clean 503 (the rest of the app
is unaffected). Configurable via `AVALANCHE_OLLAMA_URL` / `AVALANCHE_OLLAMA_MODEL`.

**Test:** `python -m pytest` from the app root. Tests use a hermetic synthetic bake
(`tests/synthetic_baked.py`) — no rasterio, no real `DATA\`, fast and safe.

**Adding an API endpoint:** add the function (in `assess.py`/`risk.py`/etc.), wire the route in
`api/stage3.py`, add the type + fetch helper in `frontend/src/lib/twin.ts`, add a test. Keep them in sync.

## 6. Gotchas that will bite you

**The `app\` package shim.** There is an `app\__init__.py` at the app root whose only job is to
`extend_path` onto `backend\app`. That is why `python -m app.bake` and `uvicorn app.main:app` work from
the project root even though the real code lives in `backend\app\`. It looks like dead code. **It is not.**
Deleting it breaks every command and the launcher. (Commands also work from `backend\`, where `app` resolves
directly — the launcher does exactly that.)

**Runtime is rasterio/pyproj-free — keep it that way.** `import app.main` must not pull rasterio, pyproj,
pandas, pyarrow, geopandas, laspy, sqlalchemy, pillow, matplotlib, or pyyaml. Those are **bake-time only**
(`processing\*`, `services\{tiles,cache}.py`, `bake.py`). If you make the runtime import one of them, you
have re-coupled the service to the geospatial stack and broken the slim deploy. There is an import-blocker
check in the verification history; re-run it if you touch imports.

**The launcher is a compiled binary.** `MountHosmerDigitalTwin.exe` is committed at the app root and is what
users double-click. Editing `launcher\Program.cs` changes **nothing** until you rebuild with the .NET 9 SDK.

**LiDAR IS used now (this reversed).** Older docs say LiDAR is unused (61.9 % coverage, 30 m Copernicus
fallback) — that was the *legacy 30 m* pipeline. Stage 3 bakes the **5 m terrain engine**, which mosaics the
LiDAR DEM/DSM to **99.9 %** AOI coverage. The 171 `.laz` point clouds are still unused (the DEM rasters are
derived from them); Copernicus is gap-fill only.

**Assess takes ~10–15 s.** A big storm lights up ~40 release zones; `assess.py` simulates runout only for the
top-12 (`MAX_SIM_ZONES`) for speed and readability. That is tuning, not a bug. A perf pass is a known
follow-up.

**Windows-only paths.** Everything is `D:\`-rooted and PowerShell-first. The correct root is
`D:\school\capstone\Avalanche\`.
